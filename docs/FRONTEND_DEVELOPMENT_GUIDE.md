Why each one, for this app specifically (not a generic definition):

- **Next.js App Router**: the app's page list (`/login`, `/dashboard`, `/dashboard/doctors`, `/dashboard/doctors/[id]`, `/dashboard/patients`, `/dashboard/patients/[id]`, `/dashboard/appointments`, `/dashboard/profile`) maps directly onto folders under `src/app` — no separate router config file to keep in sync with the page list. The alternative (a single-page app with a client router library like React Router) would mean re-implementing route-based code splitting and layouts by hand; Next.js's nested `layout.tsx` files already give this app its two shells (root shell in `src/app/layout.tsx`, authenticated shell with sidebar/topbar in `src/app/dashboard/layout.tsx`) for free.
- **Tailwind CSS**: every page in this app reuses the same small set of surface/border/text tokens (e.g. `border-slate-200 bg-white dark:border-slate-800 dark:bg-slate-900` appears identically across doctor, patient, and appointment pages). Utility classes keep that repetition visible and consistent instead of hiding it behind a growing pile of ad-hoc component stylesheets.
- **Axios + one shared instance**: every list/detail page needs the same two things — a base URL and an `Authorization` header. `src/lib/api.ts:5-17` does this once (see §3). The alternative, calling `fetch` directly in each `lib/*.ts` fetcher, would mean repeating the token-attachment and 401-redirect logic in every file.
- **TanStack Query**: doctors, patients, and appointments are genuinely shared, overlapping server data — a doctor's detail page embeds that doctor's own patients (`src/app/dashboard/doctors/[id]/page.tsx:31-36`), and dashboard cards depend on the same underlying tables. TanStack Query's cache-by-key model (see §4-§5) is what makes "a patient was added elsewhere, refresh every view that could show it" tractable without manually wiring `useEffect` refetches between unrelated pages.
- **Recharts**: the dashboard needs two chart shapes — a horizontal bar list (patients-per-doctor, doctors-by-specialization, conditions) and a time-series bar chart (14-day registration trend). Recharts gives both with a small, declarative component tree (`<BarChart>`, `<Bar>`, `<XAxis>`, `<YAxis>`, `<Tooltip>`) instead of hand-computing bar widths/heights as inline styles.
- **sonner**: `AppointmentFormModal`, `PatientFormModal`, `DoctorFormModal`, and the doctors/patients/appointments list pages all call `toast.success(...)` / `toast.error(...)` after a mutation resolves. One `<Toaster />` mounted once in `providers.tsx` is enough for every page to fire toasts without each page managing its own toast state.
- **lucide-react**: consistent icon set (nav icons in `Sidebar.tsx`, action icons in table rows, status icons) — one dependency instead of mixing inline SVGs.
- **clsx + tailwind-merge (`cn()`)**: components like `Button` and `Sidebar` take a `className` prop and also apply internal conditional classes (e.g. `collapsed && "justify-center px-0"` in `Sidebar.tsx:61-64`). `cn()` merges these without later Tailwind classes silently losing to earlier conflicting ones.

## 3. The Shared Axios Instance (`src/lib/api.ts`)

```ts
// src/lib/api.ts:5-32
export const api = axios.create({
    baseURL: process.env.NEXT_PUBLIC_API_URL,
});

api.interceptors.request.use((config) => {
    if (typeof window !== "undefined") {
        const token = window.localStorage.getItem(TOKEN_STORAGE_KEY);
        if (token) {
            config.headers.Authorization = `Bearer ${token}`;
        }
    }
    return config;
});

api.interceptors.response.use(
    (response) => response,
    (error) => {
        if (
            typeof window !== "undefined" &&
            error.response?.status === 401 &&
            window.location.pathname !== "/login"
        ) {
            window.localStorage.removeItem(TOKEN_STORAGE_KEY);
            window.location.href = "/login";
        }
        return Promise.reject(error);
    }
);
```

Key points, verified from the file:

- The JWT is stored in `localStorage` under the key `"doctor_tracker_token"` (`api.ts:3`), not in a cookie.
- The request interceptor attaches `Authorization: Bearer <token>` to every outgoing request if a token exists (`api.ts:9-17`).
- The response interceptor is the app's global session-expiry handler: any `401` response anywhere in the app clears the token and hard-redirects to `/login` via `window.location.href` (`api.ts:19-32`) — a full page reload, not a Next.js router navigation, which also resets all in-memory state (including the TanStack Query cache).
- `getAssetUrl()` (`api.ts:57-61`) strips `/api` off `NEXT_PUBLIC_API_URL` to get the backend's origin, then prepends that origin to relative paths like `/uploads/avatars/x.png` that the backend returns. This exists because the avatar image is served from the Express backend, a different origin from the Next.js frontend — a plain relative `<img src="/uploads/...">` would resolve against the frontend's own origin and 404.

## 4. Data Flow — Tracing "Book an Appointment" End to End

This is the fullest example in the app because it touches a modal, two supporting `<Select>` queries, a mutation, field-level validation errors, and multi-key cache invalidation.

**Step 1 — Page opens the modal.** `src/app/dashboard/appointments/page.tsx:95-98` sets `editingAppointment` to `null` and `formOpen` to `true` when the admin clicks "Book Appointment", then renders `<AppointmentFormModal isOpen={formOpen} onClose={...} appointment={editingAppointment} />` at `page.tsx:281-285`.

**Step 2 — The modal loads its own dropdown data.** `AppointmentFormModal.tsx:60-70` runs two `useQuery` calls scoped to `queryKey: ["doctors", "select-list"]` and `queryKey: ["patients", "select-list"]`, each calling `listDoctors`/`listPatients` from `src/lib/doctors.ts` / `src/lib/patients.ts` with `{ page: 1, limit: 100 }`. These are `enabled: isOpen` (`AppointmentFormModal.tsx:63,69`) — they don't fetch until the modal is actually open.

**Step 3 — Form state and submit.** On submit, `handleSubmit` (`AppointmentFormModal.tsx:119-130`) calls `mutation.mutate({...})`. Note the status field: it's only included `...(isEditing ? { status: form.status as AppointmentInput["status"] } : {})` (`AppointmentFormModal.tsx:128`) — **on create, `status` is never sent to the backend at all.** The `<Select>` for status is also only rendered `{isEditing && (...)}` (`AppointmentFormModal.tsx:215-228`), so a user booking a new appointment never even sees a status field.

**Step 4 — The typed fetcher.** `mutation`'s `mutationFn` (`AppointmentFormModal.tsx:93-95`) calls `createAppointment(input)` from `src/lib/appointments.ts:46-49`:
```ts
export const createAppointment = async (input: AppointmentInput): Promise<Appointment> => {
    const res = await api.post("/appointments", input);
    return res.data.data.appointment;
};
```

**Step 5 — Shared Axios instance → backend.** `api.post` goes through the interceptor described in §3, attaching the JWT, hitting `POST {NEXT_PUBLIC_API_URL}/appointments`.

**Step 6 — Backend defaults status to Pending.** Confirmed in the backend: `doctor_tracker_backend/src/models/Appointment.js:48-52` defines the `status` column as `DataTypes.ENUM(...STATUSES)` with `defaultValue: "Pending"`, and `doctor_tracker_backend/src/validators/appointmentValidators.js:19` marks `status` as `.optional()` in the create schema. Since the frontend never sends `status` on create (Step 3), every new appointment is created as `"Pending"` purely by the DB/model default — this is a real, deliberate business rule (a booking always starts as a request, not a confirmed slot), not an accidental omission.

**Step 7 — onSuccess: toast + cache invalidation.** `AppointmentFormModal.tsx:96-101`:
```ts
onSuccess: () => {
    toast.success(isEditing ? "Appointment updated" : "Appointment booked");
    queryClient.invalidateQueries({ queryKey: ["appointments"] });
    queryClient.invalidateQueries({ queryKey: ["dashboard"] });
    onClose();
},
```
Invalidating `["appointments"]` marks every cached query whose key starts with `"appointments"` as stale — this includes the appointments list page's own query key, `["appointments", { page, date, status, doctorFilter }]` (`appointments/page.tsx:45`), because TanStack Query invalidation matches by key **prefix**, not exact equality. Invalidating `["dashboard"]` covers the 5 dashboard queries (all keyed `["dashboard", "..."]` in `dashboard/page.tsx:18-31`), because appointment counts feed the "Appointments Today"/"Upcoming" stat cards and the status-distribution chart.

**Step 8 — Re-render.** Because both queries are now stale and their components are mounted, TanStack Query refetches automatically and the appointments table / dashboard cards re-render with the new appointment showing status "Pending".

This same trace (page → modal-local `useMutation` → `lib/*.ts` typed fetcher → shared `api` instance → backend → `invalidateQueries` → re-render) is the pattern for every create/update/delete in the app — `DoctorFormModal.tsx:53-77`, `PatientFormModal.tsx:77-104`, and the delete mutations in each list page all follow it identically.

## 5. State Management Split — TanStack Query vs. React Context

The app deliberately keeps two different kinds of state in two different places, and does not mix them:

**TanStack Query (`src/app/providers.tsx:9-19`)** owns everything that is a copy of backend data: doctors, patients, appointments, dashboard aggregates. Configured with `staleTime: 30 * 1000` and `retry: 1` (`providers.tsx:13-16`) — a 30-second grace period before a cached page is considered stale on remount, and one retry on failure before surfacing an error.

**`AuthContext` (`src/context/AuthContext.tsx`)** owns exactly one thing: who is currently logged in. It exposes `user`, `isLoading`, `login`, `logout`, and `updateUser` (`AuthContext.tsx:21-27`). On mount, it reads the token from `localStorage` and calls `GET /auth/me` to populate `user` (`AuthContext.tsx:36-51`); `updateUser(patch)` does a local, synchronous merge into the existing `user` object (`AuthContext.tsx:66-68`) with no network call — this is what lets `ProfilePage`'s avatar/name mutations (`app/dashboard/profile/page.tsx:50,59`) update the `TopBar`'s displayed name/avatar (`components/layout/TopBar.tsx:58-61`) instantly, since both read from the same Context.

Why this split, specifically here (not as a general essay):

- **If "who's logged in" lived in TanStack Query instead:** every page that needs to know the current user (the dashboard layout's auth guard at `app/dashboard/layout.tsx:14-18`, `TopBar`, `ProfilePage`) would need to either always mount a `useQuery(["me"])` with `staleTime` tuned so it doesn't needlessly refetch, or read from the cache directly with `getQueryData` and handle the "not fetched yet" case manually. Worse, TanStack Query's model is "cache what the server said, refetch when stale" — but auth state needs to change **instantly and synchronously** the moment `login()` resolves or `logout()` is called, before any network round-trip completes. `AuthContext.login` (`AuthContext.tsx:53-58`) sets `user` directly from the login response in the same tick; a Query-based approach would need an explicit `setQueryData` call anyway, at which point Context is simpler and there's no real caching behavior being used.
- **If doctors/patients/appointments lived in Context instead:** there would be no automatic way to know a given doctor/patient list is stale after a mutation elsewhere in the app. This is exactly the invalidation mechanism in §4 Step 7 — Context has no concept of "keys" or "invalidate all queries whose key starts with X." You'd be back to manually passing refetch callbacks between the doctor list page, the doctor detail page, and the dashboard page, which is the tangle TanStack Query exists to avoid (see §6 below for what happens when even one of these invalidations is missed).

The dividing line in this app is simple: if a value is **fetched from and cached against the backend and multiple pages need to stay in sync on it**, it's a TanStack Query key. If a value is **client-side, one holder, and needs synchronous reads on every render** (the logged-in user), it's Context.

## 6. Real Lessons From This Codebase

### 6.1 The query-key invalidation bug (now fixed) — how TanStack Query's cache actually works

**The underlying mechanism:** TanStack Query's cache is a dictionary keyed by the array you pass to `queryKey`. `invalidateQueries({ queryKey: ["patients"] })` does not know or care what a "patient" is semantically — it just marks every cached entry whose key **starts with** `["patients"]` as stale (so `["patients"]`, `["patients", 4]`, `["patients", {page:1}]` are all covered, but `["doctors", 4]` is not, even if doctor 4's data happens to include a list of patients). The cache has no idea that a doctor's detail view embeds patient data — that relationship exists only in the API response shape, not in the cache key.

**Why this matters here:** `src/app/dashboard/doctors/[id]/page.tsx:31-36` reads a doctor's own patients under the key `["doctors", doctorId, "patients", page]` — a `"doctors"`-prefixed key, not a `"patients"`-prefixed one. If a mutation that creates, edits, or deletes a patient only invalidates `["patients"]`, that doctor-detail view's embedded patient table is never told it's stale, and keeps showing outdated data until the user manually reloads the page.

**Current code is already fixed.** Every patient mutation invalidates both prefixes:
- `PatientFormModal.tsx:82-86` (create/update):
  ```ts
  queryClient.invalidateQueries({ queryKey: ["patients"] });
  // A doctor's detail page lists its own patients under ["doctors", id, "patients", ...] —
  // invalidate that prefix too so adding/reassigning a patient refreshes it.
  queryClient.invalidateQueries({ queryKey: ["doctors"] });
  queryClient.invalidateQueries({ queryKey: ["dashboard"] });
  ```
- `app/dashboard/patients/page.tsx:62-64` (delete): same three-key pattern.

The general rule this demonstrates: **whenever entity A's data is embedded inside entity B's API response (here, a doctor's response embeds that doctor's patients), any mutation on A must invalidate both A's own query key prefix and every B query key that could be showing A.** This isn't specific to Patients/Doctors — it's a structural fact about how key-based caches work, and it's worth stating outright as something understood, not just patched.

### 6.2 Appointment status always starts "Pending" — a deliberate business rule, not a missing feature

As traced in §4, the create path in `AppointmentFormModal.tsx:128` only includes `status` in the payload when editing; the status `<Select>` itself is conditionally rendered only `{isEditing && (...)}` (`AppointmentFormModal.tsx:215-228`). Combined with the backend model default (`doctor_tracker_backend/src/models/Appointment.js:48-52`, `defaultValue: "Pending"`), a newly booked appointment is always `"Pending"` regardless of what the admin does — there is no way to book something as pre-confirmed. This matches a real clinic workflow: a booking is a request until someone (the doctor's office) confirms it. It is enforced twice — implicitly on the frontend (the field isn't shown) and explicitly on the backend (the column default) — so even a direct API call that omits `status` still lands as Pending.

### 6.3 sonner and background/hidden tabs — a testing-methodology lesson, not a bug

`sonner` (confirmed dependency in `package.json`, mounted once as `<Toaster richColors position="top-right" theme="system" />` in `src/app/providers.tsx:25`) intentionally pauses its own auto-dismiss timers while the browser tab is hidden (not focused/visible), and resumes them when the tab becomes visible again — this is documented, built-in behavior of the library, not something this app's code controls or overrides anywhere in the codebase (no `duration`, timer-cancellation, or visibility-related code appears near the `<Toaster />` usage). If a toast appears to "disappear differently" when switching tabs during manual testing, that's this library behavior, not an app defect — worth remembering as a testing-methodology point: reproduce a suspected toast-timing bug in a single, continuously-focused tab before concluding the app's code is at fault. (This is a fact about the sonner library's general behavior, not something independently verifiable by reading this app's own source beyond confirming sonner is in fact the toast library in use — which it is.)

## 8. Quick Reference — Common Symptoms

| Symptom | Where to look |
|---|---|
| A list is stale after a create/edit/delete elsewhere in the app | Check the mutation's `onSuccess` — does it invalidate every `queryKey` prefix that could be showing this entity, including embedded views? See §6.1. |
| New appointment doesn't show a status picker | Expected — see §6.2, status is intentionally not user-settable at creation. |
| Toast seems to vanish inconsistently while switching tabs during testing | Not a bug — see §6.3, re-test in one continuously focused tab. |
| Avatar image doesn't load | Check `getAssetUrl` (`src/lib/api.ts:57-61`) is resolving against the backend origin, and that the backend's avatar route sends a cross-origin-friendly resource policy header. |
| Redirect loop to `/login` | Check `src/lib/api.ts:19-32` (401 handler) isn't firing on a request that should have succeeded, and that `AuthContext.tsx:36-51`'s `/auth/me` bootstrap call is reachable. |
